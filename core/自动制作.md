# 自动制作 CLI 与数据

作者只需描述目标；以下命令由队长执行。根路径为小说项目，程序位置为 `.novel-workshop/bin/novel.mjs`。CLI 不调用外部模型；宿主原生 subagent/workflow 启动独立岗位子代理完成创作与语义判断，队长负责串行收集提交。完整流程见[制作手册](手册.md)，任务结果见[派单协议](派单.md)。

## 接手与诊断

```powershell
node .novel-workshop/bin/novel.mjs doctor . --json
node .novel-workshop/bin/novel.mjs init . --title 新书 --mode 原创 --start 0 --chapters 121 --words 4000 --interval 5
node .novel-workshop/bin/novel.mjs import . --mode 改编精修 --body 正文改编/章节 --baseline "docs/原版校勘/正式校勘本.txt" --start 0 --end 622 --length source --interval 10
```

doctor 未登记时只读发现既有项目；import 不搬动、不改写原章稿、不继承未经核实的通过结论。支持数字TXT/MD文件、`第NNN章-vX.md`及0号引子；同章同版本重复文件会报错。底本支持数字或中文章号、上下分段同章、引子，编码可指定 `--encoding gb18030`。

import 后，原项目 `00-状态.md` 若存在先存到工坊的接手快照，原docs和旧进度文件保留。权威状态转入 `project.json`；`00-状态.md` 和当前要求摘要由工具生成。旧项目的“已写”与“已审”分开，接手后按当前授权核实范围。

`doctor --fix` 只安全登记中断后遗漏的文件、创建缺失的两更文档骨架及刷新生成摘要，不修改小说内容，不自动增加验收。外部改写过的旧版本仍标为失效；核实后用 write 保存新版本并复验。

## 首次参数确认

mode、全书计划章号、篇幅政策、interval 必须有明确来源。init/import 真正传入的参数和已核实资料可以登记；未传参数的默认值只是建议。doctor 的 configure 指出缺项，队长先查现有用户指示与文档，仍缺失才集中一次询问。已有明确参数不重复问，必要回答未到不开始依赖它的制作。

config 可以接收 JSON 文件，也可直接给参数并把 --source 作为来源说明：

```powershell
node .novel-workshop/bin/novel.mjs config . --mode 原创 --start 1 --end 120 --words 4000 --interval 5 --length fixed --source "用户明确要求全书120章、每章约4000汉字、每5章复审"
node .novel-workshop/bin/novel.mjs config . --source .novel-workshop/drafts/参数确认.json
```

JSON 示例：

```json
{"mode":"改编精修","plan":{"start":0,"end":622},"length":{"type":"source","minRatio":null,"maxRatio":null},"interval":10,"source":"现行要求：保留0号引子，按各原章篇幅制作，每10章复审"}
```

存在配置参数 flags 时 --source 是依据文字；仅 --source 时是 JSON 路径。固定篇幅需要 words；按底本政策不必强行要求固定字数，minRatio/maxRatio 只有作者明确规定才设边界。

## 有效授权

```powershell
node .novel-workshop/bin/novel.mjs scope . --mode continue --from 420 --to 470 --interval 10 --source "用户本轮要求写至470" --revise-approved
node .novel-workshop/bin/novel.mjs scope . --mode review --from 410 --to 470 --source "用户要求只审阅现稿"
node .novel-workshop/bin/novel.mjs scope . --mode pause --source "用户暂停续写"
```

只登记实际获得的授权。范围变更保留历史，使用最新版本。`--deliver` 表示本轮包含导出，`--format word`等记录实际交付格式，未指定则全部；`--revise-approved` 表示已有授权允许修订范围内通过稿，不让作者逐章批准普通返修。范围外草稿保留，不重新计数或自动删除。

gate 记录已存在的规划与批准依据：

```powershell
node .novel-workshop/bin/novel.mjs gate . --through 3 --evidence "docs/现行计划.md" --source "用户已批准该计划，四阶段资料已核对"
```

gate只能签G0—G3；G5必须由全书最终审阅产生。阶段签认仍需实际阅读对应资料，不把一个存在的文件当作内容完成证明。

## 要求、事实、问题、经验和资料

写JSON到工坊临时文件后，用 `record . --kind <类型> --source <JSON>` 提交。字段支持：

| 类型 | 必需内容 | 其他常用内容 |
|---|---|---|
| requirement | text、source | id、key、from、to、supersedes、status |
| fact | text、evidence | id、from、to、entities、type、dueAt、state |
| issue | text、evidence | id、from、to、severity、requiresUser、status、resolution |
| experience | text | id、from、to、status |
| material | path、kind | title、origin、id |

证据 `evidence` 形如 `{"path":"09-正文/第001章-v1.md","quote":"文件中真实存在的一句话"}`，工具验证引文实际存在。作用范围默认全书，按真实生效范围缩小；实体相关事实可按 entities 过滤，map的 factIds 可显式绑定。type为foreshadowing的事实可设 dueAt 与 state，prepare 显示未关闭到期伏笔。

要求与事实同ID更新会递增修订，保留历史；requirement同key的新项自动替代旧项，也可supersedes指定旧ID。active有效，superseded已替代，retired停用。问题状态为open、resolved、retracted、superseded；关闭/撤销需resolution，resolved要提供修复后证据。requiresUser仅用于资料无法确定、确需作者取舍的问题，不能用来转交普通修复。

原作提炼资料登记 `kind: analysis, origin: original`，改编方案登记 `kind: adaptation, origin: adaptation`，底本为source；导出原作汇编不会选入改编资料。

## 本章映射与制作

`map --source` 的示例：

```json
{"chapter":420,"sourceIds":[420],"treatment":"联动","outline":"06-细纲/第420章.md","dependencies":[419],"entities":["甲","乙"],"factIds":["F1"],"entryState":"承接419章已经交代的伤势"}
```

treatment支持保留、改写、合并、删除、新增、校正、联动；合并可有多个sourceIds。baselineTreatment保存首次分类，后续升级不改原始基线。

```powershell
node .novel-workshop/bin/novel.mjs prepare . --chapter 420 --json
node .novel-workshop/bin/novel.mjs dispatch . --role 文笔 --action write --chapter 420
# 队长用宿主原生工具启动子代理，绑定真实子代理标识
node .novel-workshop/bin/novel.mjs task . --id TASK_ID --status running --agent HOST_AGENT_ID
# 子代理仅写派单返回的 result.json，完成后由队长收集
node .novel-workshop/bin/novel.mjs collect . --id TASK_ID
```

文笔结果包含含章标题的完整Markdown text、title摘要字段与 finish 数据：`{"notes":"本章新增事实和后章提醒","experience":"具体有效手法或需避免的问题","exitState":{"伤势":"仍未痊愈","物品":"药盒由乙携带"},"entities":["甲","乙"],"factIds":["F1"]}`。每单只写一章，collect 完成后再派下一章；工具关联新版本、两更、有效经验和接续状态。中断回执用 finish 动作派给文笔，队长不绕过任务写正文。

正文按去掉标题后的Unicode汉字计量。改编明确按映射底本时，未规定的比例只提示；是否有场景删失、凑数由复核子代理判断。config可提交：

```json
{"interval":10,"length":{"type":"source","minRatio":null,"maxRatio":null},"metadata":{"author":"作者","description":"作品简介","language":"zh-CN","cover":"封面.png"}}
```

minRatio/maxRatio为作者明确要求的边界，没有要求就保留null。cover支持PNG/JPEG，用于EPUB封面。

## 复审草稿与提交

```powershell
node .novel-workshop/bin/novel.mjs dispatch . --role 复核 --action review --from 420 --to 429
node .novel-workshop/bin/novel.mjs task . --id TASK_ID --status running --agent REVIEW_AGENT_ID
node .novel-workshop/bin/novel.mjs collect . --id TASK_ID
```

复核派单提供带真实版本和依据快照的草稿，以及context.packets中的逐章JSON材料包；复核子代理读取这些文件和实际正文，填写result.json，由collect提交：

- verdict为passed或rework，summary记录实际范围和结论。
- 每章outlineComplete、requirementsMet、logicChecked、styleChecked如实填写；evidence引用该章当前版本。改编必须填写lengthReason说明场景完整性和篇幅判断。
- grades每个维度填写grade与reason。原创为符合要求/剧情逻辑/文字质量，改编另含改编符合性/删改合理性/文风一致性；通过要求全部A或B。
- rework可带issues数组，每项from/to必须完全属于实际被审章节，省略to按from保存，evidence须来自该范围内的当前被审版本。
- kind由任务动作确定；普通review只能是batch，final-review才是final。逐章检查必须是布尔值，字数和比例由工具实际计算。

accept 仍可生成指定章号或范围的审阅草稿，生成不等于通过；review 直接入口与正文入口均需要对应真实子代理任务。引文或版本不符拒绝提交，复核不能与文笔是同一个执行者。要求、事实、篇幅策略、细纲、映射、底本、入章状态或依赖章版本/出章状态变化使受影响审阅失效，既有报告保留。某章新版本未审可采用旧有效通过版作阶段稿，正式全书只采用完成最终验收的当前版本。

## 交付

```powershell
node .novel-workshop/bin/novel.mjs merge . --edition partial --from 0 --to 470 --format txt,docx,epub
node .novel-workshop/bin/novel.mjs dispatch . --role 复核 --action final-review
node .novel-workshop/bin/novel.mjs merge . --edition final --format all
node .novel-workshop/bin/novel.mjs merge . --artifact source --format txt
node .novel-workshop/bin/novel.mjs merge . --artifact analysis --format docx
```

final前须启动独立复核子代理、绑定并收集全书最终审阅。每次导出在配置的成书目录生成带新编号的文件和目录清单，不覆盖旧文件；阶段稿名含范围。Word含章节链接、分页与页脚页码，EPUB含目录、作者、简介、语言及可选封面；工具核对实际交付文件，丢失后安排重新导出并递增版本。导出不依赖Word安装，版式变更或交付另有要求时按要求渲染检查。

## 破格申请、熔断与复盘校准

```powershell
node .novel-workshop/bin/novel.mjs record . --kind exception --source 申请.json   # text/cost/from/to
node .novel-workshop/bin/novel.mjs config . --source 配置.json                    # maxRepairRounds（默认3）
node .novel-workshop/bin/novel.mjs calibrate . --source 校准.json                 # outline/note
```

| 命令 | 登记内容 | 触发与效果 |
|---|---|---|
| `record --kind exception` | 破格申请：`text` 想突破什么、`cost` 代价、`from`/`to` 影响范围、`status`（pending/approved/rejected/withdrawn）、`source` 裁决依据 | `pending` 时 doctor 给 `exception-decision` 并要求用户裁决；`approved` 进入 `prepare` 的 `exceptions`，正文可按批准内容执行 |
| `config` 的 `maxRepairRounds` | 每章允许的连续返修轮数（默认 3） | 当前范围内同章连续 rework 达阈值，doctor 与写入口停笔；其他范围的历史返修不阻塞当前任务 |
| `calibrate` | 批次复盘：`review` 审阅ID、`outline` 实际核对过的后续细纲章号、`note`、`source` | 绑定当前范围相关通过报告，仅核对当前授权内下一批且细纲须存在，未登记不能继续写 |

三者都不改写正文：申请是提议，熔断是暂停，校准是调整后续依据。裁决与校准均留痕，后续审阅可引用。

熔断后获得作者新决定，用 `calibrate` 记录 `{"chapters":[420],"note":"作者决定调整本章冲突目标，已重做细纲","source":"用户实际新决定"}`，只恢复指定章此前的连续返修计数；不能静默提高 maxRepairRounds 代替处理根因。正常批次校准派剧情子代理，产物与相关文件先核对后收集。

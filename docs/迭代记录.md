# 0.3.0 六岗位子代理与首次参数检查

2026-10-25：将同上下文切帽改为宿主原生子代理分工，保留作者只使用一个主会话的工作方式。

- 队长只诊断、派单、收集提交和汇报；主编、世界、剧情、人物、文笔、复核由独立子代理承担。dispatch/task/collect 保存任务、执行者、材料与结果，每张文笔任务仅一章，复核与文笔身份独立。
- 子代理只写隔离任务目录，正式文件和主账由队长串行提交；模型/权限沿用宿主，不引入额外后台或模型依赖。Codex技能明确调用原生子代理，DSH入口启用实际宿主分工能力。
- 首次诊断检查模式、计划章号、篇幅政策与审查间隔是否有明确来源。缺项集中询问并用config保存来源，未显式规定的默认值不冒充作者要求。
- 修复已确认的问题：依赖章版本和出章状态变化使后章审阅失效；停笔条件在写入口执行；熔断与批次校准遵守当前范围；底本丢失给出恢复事项；已记录但实际丢失的交付文件会重新安排导出。
- 六岗卡、立项/三读提示和模板统一使用项目实际篇幅政策，移除无依据的固定4000字、改编固定比例和伏笔固定章数门槛。

本轮工程验证由队长在各功能接通后集中执行，岗位子任务没有运行测试。保持五个集成场景，不增加独立测试场景；首次统一运行四项通过，交付场景发现删除产物后版本号复用、撞上残留目录文件的问题。导出编号改为参考登记历史与实际文件后，仅定向复验该场景并通过，五个场景均取得通过结果。Codex 技能通过 quick_validate 结构校验。

覆盖结果：首次参数缺项与来源持久化、安装重入、六岗位派单/绑定/幂等收集、文笔与复核分离、旧任务取消、待裁决与熔断在写入口停笔、范围外旧熔断/校准不干扰当前范围、作者校准后恢复、依赖章版本/出章状态变化使后章审阅失效、底本丢失时的结构化恢复、交付文件丢失后重新导出，以及 TXT/Word/EPUB 同源交付。DSH 钩子通过模拟宿主覆盖写入守卫、压缩恢复与 workflow 真实身份通知；该模拟不等于 DSH 桌面会话的端到端文学验收。旧版验证结果如下保留。

# 0.2.0 自动制作迭代

目标：自动诊断小说制作状况、单会话持续制作、减少作者主动对话干预。依据四个小说制作会话及对应长篇改编实例评估，实例源目录本轮不作修改。

| 需求 | 实现入口 | 验证场景 |
|---|---|---|
| 接手既有TXT/MD、0号引子、保留原稿与目录 | project.discover/sourceIndex/registerFiles，CLI import | 场景1 |
| 统一进度与有效要求，避免多份手工主账 | project.json，save/views | 场景1、2 |
| 最新范围、暂停、只审不改、尾批 | scope/history，diagnose/dueBatch/write | 场景2 |
| 单会话自动诊断到制作完成 | doctor→prepare/write→finish→accept/review→doctor | 场景2 |
| 本章相关事实、经验、底本和伏笔 | context/relevant/sourceSlices | 场景1、3 |
| 问题发现、修复、误判撤销与局部复验 | record/submitReview/approvals/contracts | 场景3 |
| DSH和Codex共用制作核心 | 完整模块同步、项目技能、DSH守卫与压缩提醒 | 场景1、3 |
| 改编逐章篇幅，无擅设比例阈值 | lengthInfo，按底本映射，review.lengthReason | 场景1、4 |
| 阶段/最终、原作/分析/改编交付分开 | merge edition/artifact，finalApproved | 场景4 |
| TXT/DOCX/EPUB同源及导航/元数据 | book-formats，版本目录 | 场景4 |

软件验证固定为四个完整集成场景，功能完成后统一执行。Word导出还需实际打开渲染，EPUB使用独立ZIP/XML读取核对；工程证据不替代真实小说的通篇文学验收。

2026-10-25：四个集成场景均通过；统一运行取得4/4后，对后续修正只补验相关场景，未增加测试场景总数。

- 安装与接手：项目规则重复安装保留原内容；全部模块与技能引用可达；0号TXT/MD、中文底本章号及末章索引、逐章篇幅、原稿保留、原始分类保持、旧进度差异和失效资料处理均覆盖。
- 自动制作：由doctor动作驱动到本轮完成；两更可重入、尾批复审、暂停、只审不改、终点多次变更、保留范围外草稿及恢复后不重复计章均覆盖。只审任务可以报告待修项后收尾，问题保持open，不改正文，也不陷入反复要求返修的循环。
- 修复与宿主：实体相关事实、要求变更后的局部失效、虚假通过拒绝、问题进入台账、版本返修与误判撤销均覆盖；DSH用模拟宿主验证入口守卫、完整模块同步及各会话压缩提醒。
- 交付：阶段稿与正式全书、原作/分析/改编隔离、按产物类型/范围/指定格式判定交付完成、失效全书验收阻止正式导出、四种格式同源、Word导航及页码、EPUB元数据和封面均覆盖。原作汇编不能抵扣改编全书交付；仅要求Word时不会被调度器要求补齐其他格式。

独立文件验证：python-docx读取Word正文和标题；标准ZIP/XML读取DOCX及EPUB，核对EPUB目录/manifest/spine与封面图片。使用本机Word打开并生成三页PDF，已逐页检查中文、章节分页、导航目录及页码，版面正常。Codex技能通过quick_validate校验。

# 0.2.1 吸收「多核协同写作模式」的功能优点

对照旧预设的能力清单逐项取舍：角色卡、人设六件套、语言基因、章末钩子、伏笔、禁写、版本不覆盖、复审引用原句、字数策略等，v0.2.0 已经具备，不再重复实现。真正缺失的是三个闭环，本轮补上：

| 旧预设做法 | 新实现 | 谁在管 |
|---|---|---|
| 文笔想突破设定必须写「破格申请」，队长/用户裁决 | `record --kind exception`：`text`/`cost`/`from`/`to`；`pending` 时 doctor 给 `exception-decision` 并停笔；批准后进入 `prepare.exceptions` | 用户裁决，模型登记 |
| 同一章连续 3 次打回即熔断、召集校准 | `maxRepairRounds`（默认 3，`config` 可改）；连续 `rework` 达阈值给 `circuit-break`，停止返修等用户校准 | doctor 判定 |
| 每 3–5 章复盘，校准宪法与台账 | `calibrate`：绑定上一份通过审阅，登记 `outline`（动过的细纲章号）与 `note`；未登记不给开下一批 | doctor 调度，模型登记 |

实现位置：`bin/project.mjs`（record 新 kind、calibrate、状态迁移与默认字段）、`bin/production.mjs`（异常裁决、熔断、校准任务与 `prepare.exceptions`）、`bin/novel.mjs`（命令、`config.maxRepairRounds`、`check` 退出码）。

## 验证结果

2026-10-25：统一运行 5/5 通过。新增场景覆盖：破格申请 pending→裁决→进入 prepare；连续三次 rework 触发熔断；提高阈值并通过审阅后出现 calibrate，登记后消失。原有四个场景全部保持通过。DSH 侧重新安装 bundle 0.2.1 并同步 `~/.dsh/novel-workshop`；钩子规则新增破格/熔断/校准一条。


真实长篇实例仅执行只读doctor发现，识别其既有章稿、0号引子、正式底本和参考入口，并发现磁盘章稿与旧进度记录不同；本轮未导入或改动该小说。软件验证使用合成文本，不宣称完成真实全书的文学质量验收。
